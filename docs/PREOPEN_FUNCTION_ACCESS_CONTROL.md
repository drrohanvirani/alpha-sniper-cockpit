# Pre-open function access control — prepared only

Status: proposed repository repair; not deployed or merged.
Scope: the zero-argument `public.alpha_lock_capital_owner_preopen()` function only.
Base: `main` at `268064ecd0c3b957403138044ded1302f50e074c`.

The owner reports that this SECURITY DEFINER function currently grants execution
to PUBLIC, anon and authenticated. The owner also reports that related pre-open
cron jobs are disabled. Codex did not inspect or modify production for this repair.
No cron job is changed or enabled by these files.

## Forward migration

File: `supabase/migrations/20260907141704_preopen_function_access_control.sql`.
The filename was generated by Supabase CLI 2.116.0 using `migration new` in an
unlinked local scratch directory. The file contains only:

```sql
REVOKE EXECUTE ON FUNCTION public.alpha_lock_capital_owner_preopen() FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.alpha_lock_capital_owner_preopen() TO postgres, service_role;
```

| Principal | Intended effective EXECUTE |
| --- | --- |
| postgres | Allowed |
| service_role | Allowed |
| PUBLIC | No grant |
| anon | Denied |
| authenticated | Denied |

No CREATE OR REPLACE FUNCTION, body change, ownership change, default-privilege
change, role-membership change, schema change, RLS change or other-function grant
is included. There is no CASCADE. If dependent grants prevent a REVOKE, stop and
review the ACL rather than broadening this migration.

The exact zero-argument signature is the requested repair target. The live body
and complete ACL/role-membership export are not in this repository. Before any
separately approved deployment, confirm that signature, SECURITY DEFINER status,
owner, effective grants, role memberships (including SET ROLE paths), legitimate
backend callers and relevant event triggers using read-only evidence. If another
overload or an inherited access path exists, stop for review; this migration does
not silently alter other functions or role memberships.

Revoking function EXECUTE controls entry to this RPC. Route-table RLS alone does
not establish access restrictions for a SECURITY DEFINER function.

## Regression test

File: `supabase/tests/preopen_function_access_control.sql`.

Run only in an explicitly approved isolated database with the existing function,
relevant Supabase roles and a representative permission setup already restored.
Do not replay the superseded historical migration to create that fixture. Do not
point this test at production; its transaction applies the new ACL temporarily.

Example for that isolated environment, using its configured local psql connection:

```sh
psql -X -v ON_ERROR_STOP=1 -v ACL_TEST_ISOLATED=yes -f supabase/tests/preopen_function_access_control.sql
```

The acknowledgement is a human safety check, not proof of database isolation.
No connection string or credential belongs in this document or chat.

Test logic:

1. Fail if the existing zero-argument SECURITY DEFINER function or required roles
   are absent, or if unexpected same-name overloads exist.
2. Snapshot the actual function definition and complete pg_proc row BEFORE the
   migration; also snapshot all other function catalog rows.
3. Include the actual migration file using psql `\ir`; apply it twice to check
   idempotency. Do not duplicate its implementation inside the test.
4. Assert `has_function_privilege(..., 'EXECUTE')` is false for anon and
   authenticated, including inherited privileges.
5. Expand the function ACL, including NULL/default ACLs, and assert no EXECUTE
   entry exists for PUBLIC (the pseudo-role with grantee OID 0).
6. Assert postgres and service_role retain effective EXECUTE and existing public
   schema USAGE. These are permission assertions, not execution of business logic.
7. Compare `pg_get_functiondef` before and after, and compare all target pg_proc
   fields except proacl. Verify other functions were not added, removed or changed.
8. Assert the second application leaves the same ACL and roll back the test.

The committed regression does not invoke any business function. An isolated
production-definition fixture is still needed to validate it against the exact
deployed definition and permission topology before deployment approval.

## Validation performed during preparation

- Passed the test's PostgreSQL statements in an in-memory PostgreSQL 18.3 runtime
  (PGlite 0.5.8), using a harmless local zero-argument SECURITY DEFINER fixture.
- Passed with both explicit PUBLIC/anon/authenticated grants and implicit default
  PUBLIC grants (NULL ACL).
- Passed eight assertions per positive scenario, including body/metadata
  preservation, other-function preservation and repeat-application stability.
- Additional local-fixture invocations returned permission-denied SQLSTATE 42501
  for anon/authenticated and succeeded for service_role/postgres.
- Negative controls correctly rejected missing REVOKE, missing service_role GRANT,
  inherited anon access, body mutation, unrelated function mutation, unexpected
  overloads and a missing target.
- Confirmed test rollback restores the fixture's original definition and ACL.
- Confirmed the functional rollback SQL below restores the reported broad access
  on the isolated fixture.

The local scratch harness expanded psql include directives and executed the SQL
in PGlite. Native psql execution, its acknowledgement directives, the actual live
function body, production role topology and PostgREST behavior were not tested.
No Supabase project was linked or contacted. Scratch tooling and fixture code are
not part of the repository change.

## Rollback SQL — documentation only, separate approval required

This forward-only proposal adds a new migration and does not rewrite history.
Prefer aborting/rolling back an uncommitted deployment transaction on failure.
After a committed deployment, a compensating migration would require its own
approval and filename; do not edit an applied migration or migration history.

The following functional rollback restores the owner-reported broad execution
access. It deliberately reopens the permission risk and must not run automatically:

```sql
GRANT EXECUTE ON FUNCTION public.alpha_lock_capital_owner_preopen() TO PUBLIC, anon, authenticated;
```

This preserves postgres/service_role access. It is NOT an exact reconstruction of
an uncaptured prior ACL: original grantors, grant options and whether backend
grants were explicit or inherited are unknown. Before any approved deployment,
capture the target's owner, proacl/default expansion and relevant memberships.
Use that evidence if exact ACL restoration is required. No broader role or
function privilege changes are authorized here.
